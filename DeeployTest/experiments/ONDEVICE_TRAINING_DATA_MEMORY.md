# On-device training-data memory placement (Siracusa) — how the FT window pool is stored & streamed

**Date:** 2026-07-22
**Purpose:** Document, from the actual generated code + linker script, where the on-device fine-tuning
data (the FT window pool) lives on Siracusa, how it is fed to the network, and what really limits how
much FT data we can use — so we know whether "30 % of the batch" is a hardware limit or a choice.

Investigated on the `speechnet_train_head_ep40_isft_fw` training fixture (S01, head-only, 30 % data =
54 windows, n_accum 4, 40 epochs). All claims verified in the generated build, not inferred.

---

## TL;DR
- The FT data pool is **54 separate per-window buffers** (`testData_mb0_buf0 … mb53`), fed **one window
  at a time** (effective batch-1). The whole 30 % is **never** assembled into a batch in L2/L1.
- The pool lives in a **dedicated 4 MB on-chip SRAM bank `WEIGHTMEM_SRAM`** (shared with the model
  weights) — **not** external DRAM, and **not** the 2 MB L2 activation arena.
- Per training step only **one window (38.3 KB) + its tiled activations** occupy L2/L1; the conv tiles
  that single window's activations L2↔L1. Peak working memory is per-window and **independent of pool size**.
- **The soft limit on FT data is the 4 MB WEIGHTMEM_SRAM** (weights + data): ~55 % (~100 windows) fits
  on-chip; 70–100 % overflows it and would need the **L3-offload path** (harness already L3-aware) at a
  per-window DMA cost. So **30 % was a choice well within budget, not an L1/L2 limit.**

## Evidence

### Memory hierarchy (Siracusa)
| level | size | role |
|---|---|---|
| L1 (cluster TCDM) | 128 KB | compute working set (one tile) |
| L2 arena | 2 MB | activations / tiling buffers (`DeeployNetwork_MEMORYARENA_L2`) |
| **WEIGHTMEM_SRAM** | **4 MB** | weights **+ FT data pool** (on-chip, CPU-accessible) |
| L3 / HyperRAM | external, large | optional overflow (harness supports via `l3_aware_copy`) |

`install/pulp-sdk/rtos/pulpos/pulp/kernel/chips/siracusa/link.ld`:
```
WEIGHTMEM_SRAM : ORIGIN = 0x10800020, LENGTH = 0x003fffe0     ; = 4 MB
.weightmem_sram : { *(.weightmem_sram) *(.weightmem_sram.*) } > WEIGHTMEM_SRAM
```

### Data is per-window buffers in `.weightmem_sram`
`testinputs.h` (generated by `testUtils/codeGenerateTraining.py`) emits, per mini-batch (= one window):
```
__attribute__((section(".weightmem_sram"))) float32_t testData_mb0_buf0[] = { ... };   // 14x700 window
__attribute__((section(".weightmem_sram"))) uint8_t   testData_mb0_buf1[] = { 2,0,0,0 }; // label
... mb1 ... mb53   (54 windows total = 6/class x 9)
```
Count in the fixture: **54** `testData_mb*_buf0` arrays = the 54-window (30 %) pool.

### Network consumes one window at a time; the harness streams it
- `TrainingNetwork.c`: inputs are **pointers** (`float32_t *DeeployNetwork_input_0; …`); weights are baked
  `static PI_L2 …`. The graph processes **one** input window; block-0's Conv input is tiled into 4 tiles
  with per-tile DMA descriptors (`..._input_0_transpose_numTiles = 4`, `data_in_cmd[...]`), i.e. that
  single window's activations stream L2↔L1.
- `Platforms/Siracusa/src/deeploytraintest.c`:
  - `#define IS_L2(ptr) ((uint32_t)(ptr) >= 0x10000000u)` — on-chip (CPU-accessible) vs external L3.
  - `l3_aware_copy(dst, src, bytes)` — handles L2↔L2, **L3→L2**, L2→L3, L3→L3 transfers.
  - training loop: `for update_step in [0,N_TRAIN_STEPS): for accum_step in [0,N_ACCUM_STEPS):` — one
    window per accum step; gradients accumulate, then one SGD update. Data buffers are moved with
    `l3_aware_copy`, so the pool can be on-chip **or** external and is fetched per-window.

## What actually limits the FT data amount

Peak L1/L2 usage is per-window (fixed), so more windows do **not** grow the L1/L2 footprint. What grows
is the pool storage. With weights ≈ 60 KB and one window = 38.3 KB, in the 4 MB WEIGHTMEM_SRAM:

| data | windows | pool | fits 4 MB WEIGHTMEM_SRAM? |
|---|---|---|---|
| 30 % | 54 | 2.02 MB | ✅ (current) |
| 50 % | 90 | 3.36 MB | ✅ |
| 70 % | 126 | 4.71 MB | ❌ exceeds |
| 100 % | 180 | 6.73 MB | ❌ exceeds |

On-chip cap ≈ (4 MB − weights)/38.3 KB ≈ **~100 windows (~55 %)**. Beyond that, place the pool in
**external L3/HyperRAM** (harness already L3-aware) and DMA each window per step — feasible but slower
(external-memory latency) and more training time. Other practical limits: **training time** (54 windows ×
40 epochs = 2160 fwd+bwd passes already took a multi-hour GVSoC run; more data scales this linearly).

## Implications
- The host-side data-fraction study (`SilentWear/PyTorch_for_On_Device/exp8_fullmodel_datasize`, 30–100 %)
  is deployable: ≤ ~55 % fits on-chip as-is; 70–100 % needs the L3-offload path (a modest engineering step),
  not a fundamental blocker.
- "Effective batch-1 + n_accum" is a *compute/BN* constraint (see `experiments/reference/BN_AND_NACCUM_FINDINGS.md`),
  independent of this *data-storage* constraint. The window pool being batch-1-streamed from WEIGHTMEM_SRAM
  is why more FT data costs storage + time, not peak L1/L2.
